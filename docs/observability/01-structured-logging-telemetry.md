## 1. Structured JSON Logging Architecture

In containerized and cloud-native environments (Docker, Kubernetes, Render, AWS), plain unstructured text logs (`print()` or default string logging) are difficult to parse, aggregate, and query.

The engine adopts **Structured JSON Logging** emitting machine-parsable JSON lines to standard output (`stdout`), integrated with automated token redaction.

### JSON Log Line Schema:
```json
{
  "timestamp": "2026-11-18T07:30:15.123456Z",
  "level": "INFO",
  "logger": "app.services.posting_service",
  "request_id": "c7a8b9e0-1234-4567-89ab-cdef01234567",
  "message": "Initiating parallel fan-out dispatch to 5 platforms",
  "total_platforms": 5,
  "execution_mode": "async_gather"
}
```

---

## 2. Distributed Tracing via `X-Request-ID`

Every inbound HTTP request is tagged with a unique Correlation ID:
1. If the client passes an `X-Request-ID` header, the engine adopts it.
2. If omitted, a fresh UUIDv4 is generated by FastAPI middleware.
3. The `request_id` is set in Python's `contextvars`, making it automatically available to all downstream coroutines, platform adapters, and log statements without threading parameter passing.

---

## 3. Log Redaction Verification

Before any JSON log line is serialized to stdout, it passes through `SensitiveDataFilter`:
- Input string: `"Posting to LinkedIn with header Authorization: Bearer AQV71234567890"`
- Emitted JSON log message: `"Posting to LinkedIn with header Authorization: Bearer ***REDACTED***"`
- Input string: `"Calling Telegram endpoint https://api.telegram.org/bot123456789:ABCDefgh/sendMessage"`
- Emitted JSON log message: `"Calling Telegram endpoint https://api.telegram.org/bot***REDACTED***/sendMessage"`

This guarantees compliance with SOC 2 Type II audit logging invariants.
